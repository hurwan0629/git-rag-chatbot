# 검색·답변 생성 테스트 리뷰

[[docs/tests/retrieval-generation/plan|계획·구현 기준]] · [[docs/tests/retrieval-generation/validation|검증 기록]]

## 검색

현재 고정 질문의 Hit@5는 **4/5**입니다. 후보 AI 랭킹 질문은 실제 `candidate_selector.py` 대신 설계 문서와 과거 병합 로그를 가져왔습니다. 문서에 함수 설명은 있었지만 구현 파일을 직접 찾은 것으로 계산하지 않았습니다.

다음에는 코드/설계/로그별 필터와 파일 단위 중복 완화, 함수명·경로를 활용한 키워드 검색 결합을 검토합니다. 여러 문서가 같은 주제를 설명할 때 Top K가 유사한 문서로 채워질 수 있습니다. 기존 수집에서 제외된 JS/TS는 재수집 이후 평가해야 합니다.

## 답변

최초 프롬프트 1.0은 단위 테스트 설명을 실제 데이터 생성에 적용해 routing-worker 호출 여부를 잘못 설명했고, 2개 답변이 출력 512 tokens에서 끝났습니다. 프롬프트 1.1에는 출처의 적용 범위 구분·짧은 답변·추가 설명 제한을 넣었습니다. 최초 결과도 실행 기록에 남겨 비교합니다.

1.1 재평가에서는 6개 모두 EOS로 종료했지만 사실성 문제는 남았습니다. 데이터 생성 질문은 여전히 테스트 설명을 혼합했고, registry 답변은 일부 모델의 공통 클래스를 전체 모델에 일반화했습니다. 후보 선택 답변은 예정 문서와 구현 완료 로그를 섞었고, 고도 답변은 근거에 없는 함수명을 덧붙였습니다. **검색 기준 통과와 생성 답변의 사실성 통과를 구분해야 하며, 현재 생성 품질은 통과로 평가하지 않습니다.**

또한 `[S1, S3]` 묶음 인용을 발견해 서버와 HTML 모두 각 ID를 검증·연결하도록 보완했습니다. 다음 품질 개선은 구현/설계/테스트 자료의 구분, 검색 결과 선별, 답변 근거 평가를 먼저 검토합니다. 프롬프트 변경만으로 해결되었다고 판단하지 않습니다.

인용 ID가 유효해도 내용이 근거와 다를 수 있습니다. 서비스 전에는 질문별 정답 사실·출처를 확보해 사람이 평가하고, 설계·예정·과거 로그를 현재 구현으로 오인하는 사례를 별도로 점검해야 합니다. 모델 학습 여부는 이 평가 이후 판단합니다.

## 진행 상태와 서비스 제공 시 개선

현재 서버 시작은 3단계 로그, 화면 요청은 작업 중 경과 시간과 완료 후 단계별 소요 시간을 표시합니다. 후속 서비스에서는 `n/5`와 함께 **상세 단계와 실제 진행률**을 보여줘야 합니다.

| 단계 | 표시 기준 |
| --- | --- |
| 저장 파일 불러오기 | 검증한 run/전체 run, 읽은 파일/전체 파일, 전체량을 알면 bytes 비율 |
| 모델 준비 | 다운로드한 bytes/전체 bytes, 가중치 로딩은 확인 가능한 완료량 또는 준비 중 표시 |
| 질문 인코딩 | 인코딩 시작·완료·소요 시간. 완료량을 측정할 수 없으면 임의의 %를 표시하지 않음 |
| 유사도 검색 | 처리한 청크/선택 청크 전체 수 |
| 답변 생성 | 생성 token 수·경과 시간·스트리밍. 최대 출력 token 대비 비율은 예산 사용률이며 완료율과 구분 |

브라우저에 진행 이벤트를 보내려면 SSE 등의 상태 전달을 추가합니다. 실패·제외 항목을 함께 표시하고, 100%가 데이터 전부의 성공을 의미하는 것으로 오해하지 않게 합니다.
